## Where Alpha-2 MCTS would fit

The cognitive-game-framing.md tuple `G = (S, A, T, V, D, C)`
characterizes v2's runtime as a sequential decision process with
constructor C. The MCTS question is about the *policy* side:
given current `(S, A, V)`, which action sequence to dispatch
next?

Today's policy is the rule-based scheduler + DriveMix:
- Frontier items get priority bias from `combined_drive_signal`
- Mode transitions follow rule constants (max_zero_streak, etc.)
- Composite ActionKinds dispatch sequences mined by H1.x

This is policy by **rules** + **observable signals**. MCTS
introduces policy by **search over hypothetical futures** —
explicitly evaluating "if I dispatch action A at tick t, what
state do I expect at t+k, and what value does that have?".

## What MCTS would NOT mean for v2

Two AlphaGo features explicitly do NOT transfer (per cognitive-game-framing.md §"What does NOT transfer"):

1. **Naive rollouts.** AlphaGo does N rollouts per real move
   because each rollout is microseconds. v2's actions
   (`DiscoverTheory`, `DiscoverPatterns`, `EvaluatePredictions`)
   are milliseconds-to-seconds. N=100 rollouts per dispatch
   would multiply runtime cost ~100× for at most ~100× more
   information. The trade rarely pays off.

2. **Single terminal reward.** AlphaGo's reward is `{+1, 0, -1}`
   at game end. v2 has no game end; cumulative drive signal
   substitutes. Each substitution is a CHOICE, not a fact —
   already covered by H2.0's DriveMix tuning.

These constraints rule out a direct port. The realistic transfer
must be narrower.

## Two realistic transfer paths

Per cognitive-game-framing.md, two paths are admissible:

### Path 1 — MCTS only at the composite layer

H1.2 / H1.4 mint composite ActionKinds at runtime — sequences of
2 or 3 primitive actions, dispatched as one unit (per ADR 0061).
The composite catalog is small and bounded; rollouts over
composite candidates would be a *finite-depth tree search*, not
an infinite-horizon Monte-Carlo simulation.

Concrete shape:
- For each Frontier choice point in Expand mode, enumerate
  candidate composites (current set ≤ 10 typical)
- For each candidate, simulate the composite's k=2-3 steps
  using existing forward_apply machinery
- Score the simulated end-state via `normalized_drive_signal`
- Pick the composite with the best score

This is essentially **score-based composite selection** with
forward simulation. Cost per choice point: ~5-10× current rate
(forward_apply is 50% optimized per ADR 0066/2026-05-01;
running it 10× in lieu of 1× is bounded).

### Path 2 — Value-network-guided expansion (no rollouts)

Use `normalized_drive_signal` as the leaf evaluator. Skip
rollouts entirely; descend the search tree only by
value-network-guided expansion:
- At each node, score CHILD candidates using the value estimate
  the runtime ALREADY HAS (the drive signal)
- No simulation of future states; just policy-network-style
  scoring of current options
- Effectively a 1-step lookahead with value-aware pruning

This is the cheaper of the two paths. It buys some of MCTS's
benefit (better choice locally) without the rollout cost.

## Composite-layer MCTS sketch (Path 1, more ambitious)

### Data structures

```rust
pub struct CompositeMCTSNode {
    state_snapshot: RsetSnapshotKey,    // identifies (rset.version, mode, ...)
    candidates: Vec<CandidateCompositeId>,
    scores: HashMap<CandidateCompositeId, ValueEstimate>,
    visit_counts: HashMap<CandidateCompositeId, u32>,
}

pub struct ValueEstimate {
    drive_signal: f64,                  // post-simulation drive_signal estimate
    confidence: f64,                    // 1 / sqrt(visits + 1)
}
```

### Loop sketch

```rust
fn select_composite_via_mcts(rt: &AutonomousRuntime,
                              budget: u32) -> CompositeId {
    let candidates = enumerate_composite_candidates(rt);
    let mut node = CompositeMCTSNode::new(rt, candidates);
    for _ in 0..budget {
        let cand = uct_select(&node);  // UCB1 selection
        let value = simulate_composite(rt, cand);
        node.update(cand, value);
    }
    node.best_by_visits()
}

fn simulate_composite(rt: &AutonomousRuntime,
                      cand: CandidateCompositeId) -> ValueEstimate {
    let mut sim_rset = rt.rset.clone();
    let mut sim_memory = rt.memory.clone();
    for step in cand.steps() {
        apply_action_simulated(&mut sim_rset, &mut sim_memory, step);
    }
    ValueEstimate {
        drive_signal: compute_drive_signal(&sim_rset, &sim_memory),
        confidence: 1.0,  // single rollout; no variance estimate yet
    }
}
```

### Cost estimate

Per choice point: `budget × steps_per_composite × forward_apply_cost`.
With budget=10, steps=2, current per-axiom forward_apply ~1ms:
~20ms per choice point. Acceptable for pre-tournament evaluation,
NOT for every tick.

Restriction: invoke MCTS only on certain choice points (e.g.,
when `combined_drive_signal` is borderline; otherwise just take
the rule-based pick). This bounds total cost.

## Integration with H2.2 drive synthesis

The two halves of #12 interact:

- **MCTS evaluates candidates by drive signal.** Whichever drive
  signal is available is the value function.
- **H2.2 synthesizes new drives.** A synthesized drive's contribution
  to the value function flows directly into MCTS's leaf evaluator.

Sequencing options:

| order | rationale | risk |
|---|---|---|
| H2.2 first, then Alpha-2 | drives stabilize before MCTS pulls on them | drive synthesis is more speculative; MCTS reads from a churning value function |
| Alpha-2 first, then H2.2 | MCTS uses the existing drive function; later synthesized drives plug in | MCTS coevolves with stable value; later drive churn invalidates MCTS observations |
| **Both deferred until empirical demand** | **safest** | **none today (which is the recommendation)** |

The retrospective's "stop and observe" framing applies here. The
3-layer consolidation (0070/0071/0072) just landed and needs
empirical observation. Adding MCTS or drive synthesis without
that observation is premature.

## Risks (in addition to E.3's 5 risks for drive synthesis)

### Risk A: Cost asymmetry compounding

MCTS evaluates each candidate via simulation. Even Path 2
(value-only) requires a candidate enumeration pass per choice
point. With composite catalogs growing as H1.x mines more
sequences, the candidate set could grow. Worst-case: O(N²) in
catalog size if pairwise comparison.

**Mitigation**: hard cap on candidate count (e.g., top-K by
H1.x's frequency stats); only evaluate the top-K.

### Risk B: State-snapshot cloning

Path 1 simulation requires cloning `rset` + `memory` per rollout.
With a typical OQ#1 RSet at 50-150 edges and Memory growing
linearly, clone cost is O(rset.len() + memory.episodes.len()).
For 2000-tick run (memory ~270 episodes), each clone is sub-ms;
across 10 rollouts at every choice point with ~100 choice points
per 1000 ticks, that's 1000 clones per 1000 ticks = 1ms × 1000
= 1s. Adds 0.5% overhead at current scale.

**Watchpoint**: scales linearly. At memory 10000+ episodes the
overhead becomes 1%+. Worth profiling.

### Risk C: Value-function instability under H2.2

If H2.2 is co-active and synthesizing/retracting drives, the
value function MCTS reads is non-stationary. MCTS scores from
last hour may be invalid this hour.

**Mitigation**: invalidate MCTS state when DriveMix mutates;
this is essentially what the existing `forward_apply_cache`
already does on `rset.version()` change. Add a similar
`drive_mix_version` invalidation key.

### Risk D: Composite-of-composites (deferred per ADR 0062)

If MCTS picks composites better than rule-based, the natural
extension is "composites of composites" — recursive composition.
ADR 0062 deferred this. MCTS makes the case sharper but doesn't
unblock it without separate ADR work.

### Risk E: Constitutional review

MCTS state (the search tree) is RUNTIME data, not meta-R.
Per commitment 3, types are meta-R; the question is whether
MCTS-discovered preferences should ALSO become meta-R (analog
of how H1.x promoted action sequences to ACTION_SEQ_MARKER).

If yes, a future ADR introduces e.g., `__mcts_pref__` marker.
If no, MCTS state stays in-process.

This is a constitutional question that can be deferred; the
sketch doesn't commit either way.

## Recommended scope (if/when implemented)

In rough priority:

1. **Path 2 first** (cheaper, less risky). Use existing
   `normalized_drive_signal` as leaf evaluator; no
   simulation/cloning. Approximate UCB1-style selection over
   candidate composites at choice points.
2. **Empirical guard**: only invoke MCTS when
   `combined_drive_signal` is in a borderline band (e.g.,
   |signal − threshold| < 0.5). At extreme signal values, the
   rule-based pick is decisive; MCTS adds no value.
3. **Cap budget** at 10 candidate evaluations per choice point.
4. **Verification**:
   - Existing 593 lib tests still pass
   - F0 battery `stream_diamond` STILL GROWING preserved
   - Long-run multi-substrate diagnostic: recommendations
     unchanged on OQ#1 / long5k; OQ#2 still ShadowMonitor

5. **Path 1 (with simulation) only if**:
   - Path 2 produces measurable improvement on F0 battery
   - Cost is < 10% overhead at typical workload
   - State cloning doesn't blow up at memory scale 10000+

H2.2 drive synthesis (E.3) precedes Alpha-2 MCTS only if drive
synthesis is empirically motivated. Currently no substrate
demands new drive bodies; the existing 3 are sufficient.

## What this sketch does NOT do

- **Does not commit to implementation**. Both halves remain
  research direction.
- **Does not pick between Path 1 and Path 2**. The recommended
  sequence (Path 2 first, then Path 1 conditionally) is offered
  as a starting point; implementing either is a separate slice.
- **Does not specify the empirical demand**. MCTS is appropriate
  when rule-based scheduling is provably suboptimal on
  measurable axes. No such measurement exists today.
- **Does not promise performance gains**. MCTS introduces
  cost; whether it pays off is empirically testable but not
  yet tested.
- **Does not address the constitutional question** (MCTS state
  as meta-R). Flagged; deferred.
